# Архитектура

Зависимости направлены внутрь. Домен не импортирует SQLAlchemy, FastAPI, RabbitMQ и HTTP-клиент.

```
api  ───────────────►  application  ──►  domain
infrastructure  ────►  application  ──►  domain
main.py, consumer.py  собирают реализации и передают их в сценарии
```

## domain

`Payment` — бизнес-сущность, не строка таблицы. Она открывает платёж, сверяет отпечаток тела с уже сохранённым ключом, захватывает обработку на время аренды, переводит `pending` в `succeeded` или `failed` и отмечает доставку webhook. Повторный `finish` не затирает конечный статус. `OutboxMessage` отмечает публикацию.

Отпечаток запроса считается в `app/domain/request.py` по каноническому JSON. Формат суммы, валюты и размер metadata проверяет схема HTTP до входа в сценарий.

## application

Сценарии:

- `CreatePayment` — пустой ключ, допустимость webhook, идемпотентная вставка платежа и события outbox в одной транзакции.
- `GetPayment` — чтение по идентификатору.
- `ProcessPayment` — захват, вызов шлюза, фиксация статуса, доставка webhook. Шлюз вызывается вне транзакции. Повтор сообщения не вызывает шлюз, пока жив захват или статус уже конечный.
- `PublishOutbox` — публикация пачки и отметка строк. Сбой на середине не откатывает уже подтверждённые публикации.

Порты описаны в `app/application/ports.py`: репозитории, Unit of Work, шлюз, отправитель webhook, проверка адреса, публикация в брокер. Сценарий получает Unit of Work и не импортирует сессию SQLAlchemy.

## infrastructure

ORM-модели `PaymentModel` и `OutboxModel` живут отдельно от сущностей. Репозиторий загружает строку, собирает сущность и при `commit` записывает изменённые поля обратно. `SqlAlchemyUnitOfWork` держит транзакцию. На PostgreSQL чтение к обработке берёт `FOR UPDATE`, выборка outbox — `FOR UPDATE SKIP LOCKED`.

Рядом: топология RabbitMQ, публикация и consumer, эмуляция шлюза, HTTP webhook, сетевой фильтр адреса.

## api

`router` объявлен в модуле, а не внутри фабрики. `POST` и `GET` собирают команду или идентификатор и вызывают сценарий. Заголовок `X-API-Key` проверяется как транспортное требование, сравнение через `secrets.compare_digest`.

Ошибки сценария превращаются в ответ отдельными обработчиками: пустой ключ — `400`, неизвестный платёж — `404`, тот же ключ с другим телом — `409`, запрещённый webhook — `422`. Текст ответа не содержит адрес webhook и присланный ключ. Недоступность PostgreSQL в `app/main.py` отвечает `503` без текста SQL.

## Сборка

`create_app` создаёт движок, фабрику Unit of Work, сценарии и подключает уже собранный роутер. Relay outbox работает в процессе API. `app/consumer.py` поднимает тот же сценарий обработки на очереди `payments.new`.
